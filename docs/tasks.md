# 阶段 3B：任务拆解

## 1. 实现范围与顺序说明

本任务文档严格以 `tech-architecture.md` 为输入，不修改已确认的需求、UX、UI 或架构。用户明确要求本次只拆分任务、不写代码，因此所有任务初始状态均为“待处理”。

本次不生成 `api-design.md`；该文档在用户后续明确需要接口细则时再单独开展。

### 最小可运行闭环

最小闭环是“用户完成首次配置后，可以持续进行本地保存的文字对话”：

```text
TASK-001 项目骨架
  → TASK-002 SQLite 数据库
  → TASK-003 本地命令边界
  → TASK-004 API 配置
  → TASK-005 虚拟女友设定与引导
  → TASK-006 应用壳与页面入口
  → TASK-007 文字对话
```

完成闭环后，用户可以：配置并测试对话 API、设置虚拟女友、发送文字、看到回复、重启后继续同一条聊天时间线，并在 API 失败时得到恢复入口。

其余功能按以下顺序推进：语音交互 → 长期记忆 → 日程 → 后台主动陪伴 → 数据导出 → 跨平台验证。

## 6. TASK-016 现状诊断（TTS 延时）

本节的代码位置用于界定优化范围，不代表已修改任何需求或验收标准。

| 环节 | 现状 | 具体位置 | 造成的延时 |
|---|---|---|---|
| 分片连接 | 每个 4096 字节分片都重新建立 TCP+TLS，并重做 WebSocket upgrade | `src-tauri/src/edge_tts.rs` 的 `synthesize_chunk`、`connect`、`MAX_CHUNK_BYTES`、`split_text` | 长文本按分片数线性叠加连接与握手时间 |
| 合成时机 | 必须等所有分片合成完毕才返回整段音频 | `edge_tts.rs` 的 `synthesize` | 首帧音频被整段合成时间阻塞，无法边合成边播 |
| 传输 | 音频帧通过 Tauri IPC Channel 逐个推给前端（JSON + base64） | `src-tauri/src/commands/mod.rs` 的 `synthesize_speech_stream` | 分块传输，首帧到达即可播放 |
| 播放 | 前端拿到完整结果后才 `new Audio(data:...)` 再 `play()` | `src/App.tsx` 的 `playSpeech` | 解码与加载完成前没有声音 |
| 触发时机 | 自动播放发生在助手消息保存之后 | `src/App.tsx` 的发送流程 | 用户感知为“回复出现后还要再等一段” |

可选的优化方向（供 TASK-016 拆解，不引入新需求）：复用单条 WebSocket 顺序发送多个 SSML 分片或按句子减少分片；后端流式产出音频并通过事件/通道推送，前端尽早开始播放；以二进制 IPC 或本地临时文件替代 base64 data URI；文本到达后立即发起合成并与消息落库并行。

TASK-016 开始前需先确定量测口径（例如固定文本的首帧延时基线）并记录优化前后对比，避免以主观感受判定完成。

当前实现（已落地，待量测）：后端 `edge_tts::synthesize_stream` / `volcengine_tts::synthesize_stream` 每收到一个音频帧就通过 Tauri Channel 推给前端；前端 `playStreamingSpeech` 用 MediaSource（`audio/mpeg`）边收边播，去掉了按句切分、整段 base64 与 `<audio data:...>` 路径。已实测 Edge 流式合成可跑通、MP3 分块入 MSE 能正常播放。仍需在真实设备上用固定文本记录优化前后首帧延时。

> 注意：Edge 与火山引擎都是 WebSocket 流式合成，现已统一走「边收边推 + MSE 边收边播」。Edge 仍是每个 4096 字节分片新建一次连接（连接复用未做）；若要进一步降延迟可复用单条 WebSocket。
